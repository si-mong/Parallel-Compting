# HTCondor vs MPI — 파일 전송 방식과 `/scratch`

> HTCondor는 NFS 없이도 잘 돌았는데, 왜 MPI에서만 `/scratch`를 NFS로 공유해야 했을까?

## 핵심

**HTCondor는 파일을 직접 옮겨 주고, MPI는 옮겨 주지 않는다.**

## HTCondor

- 작업명세서(`.jds`)에 실행 파일, 입력 파일, 출력 파일을 적는다.
- 작업을 제출하면 HTCondor가 **실행 파일과 입력 파일을 work 노드로 보내고**, 끝나면 **결과 파일을 main으로 돌려준다.**
- 그래서 노드끼리 파일시스템을 공유하지 않아도 된다.

## MPI

- `mpirun`은 SSH로 각 노드에 **프로세스만 띄울 뿐, 파일은 복사하지 않는다.**
- 각 노드는 **자기 디스크의 같은 경로**에서 실행 파일을 찾기 때문에, 모든 노드에 같은 파일이 있어야 한다.
- 여러 노드가 **하나의 파일을 함께 읽고 쓰는** MPI-IO 예제(`26-mpi_shared_io.c`)도 공유 파일시스템이 있어야 성립한다.
- 그래서 main의 `/scratch`를 NFS로 공유하고 그 안에서 컴파일·실행했다.

## 비교

| 항목 | HTCondor | MPI |
|------|----------|-----|
| 작업 성격 | 서로 독립적인 작업 여러 개 | 서로 통신하며 협력하는 프로세스 |
| 파일 전송 | 스케줄러가 자동으로 전송 | 하지 않음 |
| 공유 파일시스템 | 필요 없음 | 필요 (NFS `/scratch`) |

## 정리

HTCondor는 **"작업 + 파일"을 묶어서 보내는 배치 시스템**이고,
MPI는 **프로세스를 실행하고 통신만 담당**한다. 파일 공유는 클러스터 구성(NFS)이 맡아야 한다.
